mksysb

または現在実行中のシステムのクローンを代替ディスクに作成します。 このコマンドは
AIX 5.3
3で廃止された。
注:
AIX 5.3

alt_disk_copy

alt_disk_install

説明
注:
AIX 5.3

alt_disk_install
コマンドは、
alt_disk_copy
、
alt_disk_mksysb
、および
alt_rootvg_op
の 3 つのコマンドに分割されています。 このコマンドに追加された新機能はありません。
alt_disk_install
コマンドは、
オペレーティング・システムを次のリリース、メンテナンス・レベル、またはテクノロジー・レベルに更新するための方法を提供するもので、
これを使うとマシンが長時間にわたってダウン状態になることがありません。 これを行うには、別のディスクに
mksysb
イメージをインストールするか、現行システムを複製してから更新を適用して次の保守レベルまたはテクノロジー・レベルに達するようにするかの 2 つの方法があります。
重要:
alt_disk_install
は、
alt

alt_disk_install

alt
prefix-
alt_disk_install

最初の機能である

AIX 4.3
以降
mksysb
のイメージ、
AIX 4.3
以降
mksysb
のテープ、または
AIX 4.3.3
以降
mksysb
の CD が必要です。
alt_disk_install
コマンドは、現在使用されていない 1 つ以上のディスクを指定して呼び出され、
mksysb
は、ユーザーが選択した場合に、次のリブートで
AIX 4.3
以降のシステムでシステムがブートされるように、それらのディスクに復元されます。
注:
alt_disk_install

AIX 4.3
mksysb

AIX 5.1

必要に応じて、新しいディスクをブートした後で

コマンドを実行し、
旧バージョンのオペレーティング・システムにブート・バックするようにブート・リストを変更できます。

第 2 の、実行中の rootvg のクローンを作成する機能を使うと、root ボリューム・グループのバックアップ・コピーを作成できます。 このコピーは、rootvg が失敗した場合のバックアップとして使用されるか、追加の更新をインストールすることによって変更される可能性があります。 一例として、4.2.0 システムのクローンを作成し、次に更新をインストールして、クローンを作成した rootvg を 4.2.1.0 の状態にすることなどができます。 この方法を使えば、システムの実行中にシステムを更新でき、その後で新しい rootvg からリブートすると、実行中のシステムのレベルが 4.2.1 になります。 このレベルに問題がある場合は、ブート・リストを 4.2.0 のディスクに戻してリブートすれば、システムは 4.2.0 に戻ります。 さらに例を挙げるなら、rootvg のクローンを作成し、個々のフィックスを適用し、システムをリブートし、適用したフィックスをテストして、問題があれば、元の rootvg に戻してリブートするということもできます。
注:
NIM 代替ディスクの移行 (バージョンまたはリリース・レベルのアップグレード) は、
AIX 5.1
以降の
nimadm
コマンドでサポートされます。 詳しくは、
nimadm

現在、上記の 2 つの機能を実行するために、4.1.4.0 以降のシステムで
alt_disk_install
コマンドを実行できます。
alt_disk_install
コマンドを実行するには、

使用される

注:
インストールする
mksysb
のバージョン・リリース保守またはテクノロジー・レベルは、
bos.alt_disk_install.boot_images

ファイル・セットのレベルと一致している必要があります。
rootvg ボリューム・グループのクローン作成時に、
bosboot
コマンドを使用して新規ブート・イメージが作成されます。
mksysb
イメージのインストール時に、
mksysb
およびプラットフォーム・タイプのレベルのブート・イメージが、新しい代替 rootvg のブート論理ボリュームにコピーされます。 システムをリブートすると、ブートの初期段階で

コマンドが実行され、システムが再度リブートされます。 これは、復元された
mksysb
とブート・イメージを同期するためです。 その後、システムは通常モードにブートされます。
インストールの終了時に、ボリューム・グループ
altinst_rootvg
は、プレースホルダーとしてオフに変更された状態のターゲット・ディスク上に残されます。 これを vary on した場合、このグループは論理ボリュームを 1 つも所有していないものとして示されますが、実際には論理グループが含まれています。しかし、これらの論理グループの名前は実行中のシステム上の論理ボリュームの名前と衝突するため、ODM からは除去されています。
altinst_rootvg
ボリューム・グループをオンに変更せずに、定義をプレースホルダーのままにしておくことをお勧めします。
システムが新しい代替ディスクからリブートした後、
alt_disk_install
バージョンが 4.3.2 以上でない限り、以前の rootvg ボリューム・グループは
lspv
リストに表示されません。
alt_disk_install
4.3.2 以上の場合
新しい代替ディスクからリブートすると、以前の rootvg ボリューム・グループが

リストに old_
rootvg

-X
フラグ (つまり、
alt_disk_install
-X
old_rootvg) でのみ除去する必要があります。
元の rootvg に戻る必要がある場合は、
bootlist
コマンドを使用して、元の rootvg からリブートするように
bootlist

どのディスクが特定のボリューム・グループのブート・ディスクであるかが不明の場合は、

代替ルート・ファイル・システムは

重要:
alt_disk_install
を使用して代替 rootvg を作成したが、それを使用しなくなった場合、または
alt_disk_install
コマンドを実行したい場合は、

単に

が実 rootvg の

この機能は、ネットワーク・インストール・マネージメント (NIM) によっても使用できます。 詳しくは、「NIM Guide」を参照してください。
AIX 4.3.1
以降のバージョンの
alt_disk_install
は、段階的に実行できます。 インストールは 3 つのフェーズに分割され、デフォルトでは 3 つのフェーズをすべて実行します。
表 1. フェーズ
項目 | 説明
Phase 1 | altinst_rootvg ボリューム・グループ、 alt_ 論理ボリューム、 /alt_inst ファイルシステムを作成し、mksysb または rootvg データを復元します。

Phase 2 | 指定されたカスタマイズ・スクリプトを実行し、更新、新規ファイル・セット、フィックス、またはバンドル (クローン作成のみ) をインストールし、指定された場合は resolv.conf ファイルをコピーし、指定された場合は NIM クライアントのままにするためにファイルをコピーします。
Phase 3 | /alt_inst ファイル・システムをアンマウントし、ファイル・システムおよび論理ボリュームの名前を変更し、 alt _ logical ボリュームを除去し、 ODM という名前を付け、 altinst_rootvg をオフに変更します。 bootlist を設定し、指定されている場合はリブートします。
各フェーズを個別に実行することも、フェーズ 1 と 2 を一緒に実行することも、フェーズ 2 と 3 を一緒に実行することもできます。 フェーズ 2 は、フェーズ 3 を実行する前に複数回実行することができます。
フェーズ 3 を実行して、使用可能な rootvg であるボリューム・グループを取得します。 フェーズ 1 および 2 を実行すると、
/alt_inst
ファイル・システムはマウントされたままになります。
フェーズ 1 か 2、またはその両方を実行した後にもう一度最初からやり直す (altinst_rootvg を除去する) 場合は、
alt_disk_install -X
コマンドを実行してクリーンアップを行います。
元の rootvg と新しい代替ディスクとの間でデータ・アクセスが必要な場合は、ブートされていないボリューム・グループで、
-W
フラグを使用してボリューム・グループ

wake-up
は、ボリューム・グループをポスト

/alt_inst

注:

altinst_rootvg
に名前変更されます。

稼働中のシステムのオペレーティング・システムのバージョンは、

old_rootvg

例えば、 4.1.5 稼働中のシステム上の

4.3.3
mksysb

から代替ディスクが作成されます。 2 つのボリューム・グループ間のデータにアクセスするには、 4.3.3 代替ディスクおよび

4.1.5

ボリューム・グループからブートする必要があります。
この制限は、

)。
FORCE 環境変数が

重要:
稼働中のオペレーティング・システムよりも高いオペレーティング・システム・バージョンを含むボリューム・グループに対して FORCE

AND

注:

制限
稼働中のシステムのオペレーティング・システムのバージョンは、
wake-up

の下にあるボリューム・グループのオペレーティング・システムのバージョン以上でなければなりません。 これは、
altinst_rootvg
および
wake-up
old_rootvg
からブートする必要があることを意味します。

例
実行中の 4.2.0 rootvg のクローンを hdisk3 に作成し、次に /updates から更新を適用して、クローン作成した rootvg を 4.2.1 レベルのものにするには、次のように入力します。
alt_disk_install -C -F 4.2.1.0_AIX_ML -l /updates hdisk3
これで、次回のリブート時には hdisk3 からブートされるように、ブート・リストが設定されます。
4.3 mksysb イメージを hdisk3にインストールするには、次のようにカスタマイズされたスクリプト (
/home/myscript
) を実行して、リブート前に一部のユーザー・ファイルを代替 rootvg ファイルシステムにコピーします。
alt_disk_install -d /mksysb_images/4.3_mksysb -s /home/myscript hdisk3
新規代替ディスクからのブート後に元の rootvg ODM データベース・エントリーを除去するには、次のようにします。
alt_disk_install -X old_rootvg
元の rootvg の
lspv
リストは、
None
に変更されます。 したがって、それらのディスク上に新規ボリューム・グループが作成される可能性があります。
複数の物理ボリュームを持つボリューム・グループのブート・ディスクを判別するには、次のようにします。
alt_disk_install -q hdisk0
以下に出力の例を示します。
# lspv

hdisk1 00076443210a72ea rootvg
hdisk2 0000875f48998649 old_rootvg

hdisk2

old_rootvg
のブート・ディスクは hdisk2です。 したがって、ブート・リストを hdisk2 にリセットし、元の rootvg ボリューム・グループにリブートすることができます。
